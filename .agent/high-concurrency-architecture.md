# 多用户与高并发改造设计

- 状态：原始设计定稿；三条核心链路已实施，实际实现与验收边界已回填 `docs/HIGH_CONCURRENCY_REQUIREMENTS.md`
- 定位：保留原始设计决策；代码路径、混合存储边界、VPS 当前状态和实测结果以 `docs/HIGH_CONCURRENCY_REQUIREMENTS.md` 为准
- 实施差异：当前保留 SQLite 业务主存储，PostgreSQL 承载队列／账号／授权及对账副本；未实现权限缓存、完整指标管理页或全业务 PostgreSQL 化，不将设计目标写成已完成能力
- 业务基线：RSS 发现 → 下载 → Scribe 转写 → 翻译 → 复核 → 审核箱 → 超时审批 → R2 发布 → 私人节目库
- 技术目标：持久化队列、多 worker、背压、限流、故障恢复、权限隔离、费用治理、可观测性与可复现压测；其中完整可观测性管理页和生产故障矩阵仍是后续验收项
- 纪律：不虚构 QPS、吞吐量或生产稳定性；mock 压测与真实付费调用分别记录

## 设计原则

- 高并发主要落在「多期有状态任务并发执行」，不是把节目库页面包装成高 QPS 系统。
- 队列是必要的基础设施；优先使用 PostgreSQL 持久化队列，不为了术语引入 Kafka。
- 现有防重复付费、unsafe 不自动重放、unknown 对账和人工审核边界不得因重构而削弱。
- 优先形成可部署、可压测、可恢复的单集群架构，不做多地域、Kubernetes 或复杂服务网格。
- 所有外部付费服务在压测中使用 fake provider；真实调用单独受控验收。

## 目标拓扑

```text
Browser / 多用户
    │
    ▼
Fastify 边缘与 Web 管理 API
    │ 鉴权、会话、请求限流、静态页、签名资源授权
    ▼
长驻 Python 领域服务
    │ 审核、override、审批、账本、任务写入；取消每请求 spawn CLI
    ▼
PostgreSQL
    │ 用户、Episode、产物、审核、审批、账本、任务与交付
    ▼
Worker 池
    │ 下载、转写、翻译、复核、看点、R2 发布
    ├── Redis：分布式限流、短期缓存、并发信号量
    ├── Scribe / 模型供应商
    └── Cloudflare R2
```

Fastify 与 Python 领域服务可以部署在同一 VPS，但必须是不同进程。领域服务通过内部地址监听，不直接暴露公网。Worker 与领域服务共享 PostgreSQL 数据契约，不通过内存状态交互。

## 核心组件

### PostgreSQL 系统记录与队列

统一保存：

- 用户、会话、角色和资源访问授权
- feed、候选、Episode、产物、审核修订、override、审批、交付
- 付费调用账本与对账状态
- 任务、任务尝试、错误、租约、优先级和费用预算

单写者 SQLite 不再承担多 worker 并发写入。迁移必须保留既有 guid、artifact hash、call_ref、审批和交付历史。

### 持久化任务队列

任务表至少包含：

| 字段 | 语义 |
| --- | --- |
| `id` / `episode_id` | 任务及业务归属 |
| `kind` | download / transcribe / translate / review / highlights / publish / rerun |
| `status` | ready / running / retry / failed / parked / completed |
| `payload` | 当前不可变输入版本与必要参数 |
| `idempotency_key` | 唯一约束，业务阶段 + 输入 hash + 版本 |
| `priority` / `available_at` | 调度顺序与延迟重试 |
| `locked_by` / `locked_until` | worker 租约与崩溃接管 |
| `attempts` / `max_attempts` | 有界重试 |
| `last_error` | 可查询的稳定错误码与安全摘要 |
| `budget` / `user_id` | 单期与单用户资源约束 |

任务尝试另存历史，记录 worker、开始／结束时间、结果、用量与错误。任务状态与业务状态更新必须在同一个数据库事务中完成。

### Worker 领取与恢复

- 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 在短事务中领取 ready／到期 retry 任务。
- 同一任务只能有一个有效租约；领取后更新 running、worker、attempts 和 locked_until。
- worker 在执行期间续约；进程崩溃后由其他 worker 在租约到期时接管。
- unsafe 付费任务接管前必须检查账本和既有任务结果，不能只凭 running 状态重新调用。
- 本地 safe 阶段可以自动恢复；付费结果未知进入 unknown／人工对账，不自动重发。
- 单任务失败不阻塞其他任务；达到重试上限进入 parked 或死信视图。

### 有界并发与背压

- 全局 worker 并发可配置，默认有界，不随任务数无限创建进程。
- 按任务类型设置并发：下载、转写、翻译、复核、发布分别控制。
- 按供应商设置并发和令牌桶速率，超限任务保持 ready／retry，不拥挤调用。
- 按用户设置最大 running 任务数与每日预算，防止单用户占满系统。
- 队列长度超过阈值时暂停新任务提交或降级为非优先处理，页面明确显示排队状态。
- 不用强杀在途子进程处理普通超时，避免制造未知付费结果。

### Redis 的职责

Redis 只保存可重建或短期协调数据：

- 按用户／IP 的请求限流
- 按供应商的分布式速率限制与并发信号量
- 热门节目列表、权限和短期查询缓存
- 可选的短期会话加速

任务、账本、审批和发布状态不得只存在 Redis。Redis 故障不得导致任务或付费调用记录丢失。

## 多用户与权限

### 账号和授权

- 用户表保存账号、密码哈希、角色、状态和创建时间；密码使用 Argon2id 或等效安全哈希。
- 登录使用安全会话 Cookie：HttpOnly、Secure、SameSite=Lax／Strict、过期与轮换。
- 角色至少区分所有者／管理员和普通体验用户。
- 资源授权明确到 feed、Episode、审核修订、交付对象和账本范围。
- 普通用户只能访问自己被授权的节目，不能读取其他用户的私有音频、字幕、override 或费用。
- 管理操作记录操作者、资源、版本、时间和结果。

### Web 与资源安全

- 替换当前共享 Basic Auth 和 `admin / admin` 演示凭据。
- 登录、写入和审批接口有 CSRF／同源保护、请求限流和完整输入校验。
- R2 签名 URL 在授权成功后按 bucket/key 和短期有效期签发，不暴露其他用户对象。
- 日志不记录密码、Cookie、Authorization、API key 或签名 query。
- 普通体验用户默认不能触发无限付费任务；创建任务需要配额和明确权限。

## 费用与配额治理

- 保留 Scribe、翻译、复核、调研、分类、看点的独立账本。
- 每期预算、每用户预算和全局预算在执行付费任务前检查。
- 预算不足时任务保持等待或 parked，不得先调用再补记失败。
- 费用页区分账本估算、模型返回成本、供应商对账和未知金额；未知不记零。
- R2 存储和 A／B 类操作仍可与 Cloudflare 控制台核对，不伪装成项目账本已覆盖。
- 高并发压测默认不产生真实费用；真实小规模验收单独列用量和成本。

## 可观测性与管理页

新增队列与运行视图：

- ready／running／retry／failed／parked 数量
- 队列深度、最老等待任务、租约异常和 worker 心跳
- 各供应商并发、限流等待、错误码和外部延迟
- 单期各阶段耗时、费用和当前版本
- unknown 付费调用和失败交付的明确待办

指标至少覆盖：

- 任务领取量、完成量、失败量、重试量
- 队列等待时间与执行时间
- API 请求速率、错误率和 p95／p99 延迟
- worker 在途任务、租约接管次数
- 付费调用用量、估算费用与 unknown 数量

结构化日志使用 task id、Episode id、call_ref 和 user id 关联，但不记录秘密或完整隐私内容。

## 从现有实现的迁移

- 先冻结并备份 SQLite，记录 Episode、artifact、ledger、approval、delivery 和 override 的数量及关键 hash。
- PostgreSQL 建立新 schema，保留原 id 或提供不可逆丢失的旧新映射；优先保留原 id 以维持现有引用。
- 迁移执行租约时可不保留正在运行的旧进程；在安全停机窗口完成迁移，避免双写复杂度。
- 将 discovered、rejected、待交付状态映射为对应任务；已有 delivered 内容只迁移发布记录，不重新执行付费步骤。
- 迁移后逐项对账数量、guid、artifact SHA256、call_ref 和当前发布版本。
- Fastify 的「每次请求启动 Python CLI」改为长驻领域服务调用，审核与审批规则仍只在 Python 领域层实现一次。
- 当前 execution_lock 的语义迁移到任务租约；单期业务互斥仍可保留为独立约束。

## 压测与故障验收

### 负载模型

- 多 feed 同时产生大量新 Episode，使用 fake RSS 和 fake provider。
- 多 worker 同时领取任务，覆盖队列积压、优先级和有界并发。
- 多用户同时读取节目库、打开大字幕详情、提交修改和审批。
- 已发布音频通过 R2 加载，不将 R2 外部能力计入 VPS 的虚假吞吐。

### 故障模型

- worker 在任务领取后、付费 intent 后、产物写盘后、状态提交前崩溃
- 外部服务超时、限流、5xx、无效响应和结果未知
- Redis 不可用、PostgreSQL 短暂连接失败、API 与 worker 重启
- 重复 HTTP 请求、重复消息、过期页面和并发审批
- 用户越权、暴力登录、超过配额和签名 URL 过期

### 验收证据

- 同一幂等任务只产生一次有效付费结果，重复 worker 不重复扣费
- 无任务丢失、无非法状态回退、无旧版本覆盖新版本
- 背压与供应商限流真实生效，队列可恢复
- 多用户资源隔离与配额限制通过
- 输出实测吞吐、延迟、队列深度、错误率和资源占用，不写未测量的高并发数字
- mock 压测通过不能替代真实小规模端到端验收

## 明确不做

- 不引入 Kafka、Kubernetes、服务网格或多地域容灾作为面试装饰
- 不把任务、账本或审批仅存 Redis
- 不为了高并发允许 unsafe 付费工具自动重放
- 不把多用户简单实现成共享账号
- 不在没有压测证据时宣称生产级高并发
- 不因重构取消人工审核、override 保护、发布后修订和私有交付边界

## 实施顺序

- PostgreSQL schema、迁移与对账工具
- 持久化任务队列、`SKIP LOCKED` 领取、租约与任务尝试
- 长驻 Python 领域服务，替换每请求 Python CLI
- Worker 池、供应商限流、背压和预算闸门
- 多用户账号、权限、会话、审计与签名资源授权
- 队列／运行管理页和指标
- mock 压测、故障注入、真实小规模验收与部署文档

每个阶段必须保留测试、恢复证据和实测结果；不得只写架构图就宣称完成。
